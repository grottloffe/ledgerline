# REFACTOR iteration — 2026-07-26

Follows `baseline-2026-07-26.md`. Five skill defects were identified there; this
records what was changed, what was learned, and — importantly — what is still
unverified.

**Status: the skill edits are UNTESTED.** Every agent run below received the
pre-edit skill text. See "The invalid run" for why, and run
`node tests/tier3/run.js canary` before believing any future result.

## What changed

| Defect | Form used | Where |
|---|---|---|
| Roadmap change used as a rubber stamp | prohibition + rationalization table + red flags | `using-superproj`, `roadmap` |
| Requirement text/priority editable to fit work in flight | prohibition, in the contract and in the only skill that would do it | `using-superproj`, `roadmap` |
| Park status undefined | stated in invariant 3 and at the refusal point | `using-superproj`, `start-feature` |
| Priority unranked against the one-in-progress rule | added as a refusal condition | `start-feature` |
| Commit target undefined | conditional on an observable predicate + invariant 8 made explicit | `start-feature`, `finish-feature`, `using-superproj` |

Guidance form follows `superpowers:writing-skills`: prohibitions only for the
discipline failures, structure for the gaps. Two supporting changes were not
documentation at all:

- **`sp.js` line 334.** The engine's own fix hint for too-many-in-progress read
  *"Move all but one back to planned or blocked"* — `planned` first — while the
  skill said never `planned`. The skill instructs agents to run `check` and fix
  what it reports, so the tool won. Documentation could not have fixed this, and
  no static lint compares a skill's rule against an engine's advice. Now reads
  "Park all but one as blocked, with the reason — not planned".
- **`ledgerNotLeftDirty`**, a new universal predicate. Asserts only that ledger
  changes were committed, deliberately silent on *where*: the branch choice is a
  real open question and the fixture's history is linear, so committing to the
  default branch is legitimate there.

## The invalid run

Four scenarios were re-run, then three again. All of them read the **old** skill
text. Confirmed three ways: the subagent transcripts contain old-only headings
(`## 3. Apply it`) and zero occurrences of any added phrase; the on-disk snapshot
contained the new text throughout; and a canary agent, asked whether a
newly-added sentence was in the skill it had been given, answered NO.

The cause is a second cache. Copying files into the installed snapshot satisfies
the tier0 disk comparison but does not refresh the in-memory registry that serves
skill bodies to agents. Nothing warned, because nothing on disk was wrong.

**`/reload-plugins` is the fix, and a version bump is not needed** — confirmed by
canary, all four edited skills answering YES immediately after a reload with the
snapshot content unchanged. The reload re-reads files from the installed
directory; the version only decides which directory that is. (For an actual
release the bump still matters, so that a clean `/plugin install` produces the
same content a hand-copy did.)

**The trap is that the invalid run looked like progress.** B4 stopped rewriting
R-005 and stopped demoting F-002 — the two failures the edit targeted — and that
was reported as the fix working. It was run-to-run variance on unchanged text.
A re-run that improves is not evidence until you have proved the agent could see
the change.

## What the invalid run is still good for

It is a valid, larger baseline of the **shipped** skills, and it produced one
finding no single run could:

Commit behaviour under the shipped text, seven runs:

| Run | Ledger committed |
|---|---|
| a3 #1 / a3 #2 | no / **yes** — identical text, opposite outcome |
| a4 #1 / a4 #2 | **yes** (feature branch) / no — same, reversed |
| b3 #1 | yes, feature branch |
| b4 #1 / b4 #2 | no / no |

3 of 7. Invariant 8 already said "never leave it dirty", so this is not a missing
rule — it is a rule that does not bind, which is exactly what variance measures.
Both a3 and a4 flipped between identical runs; b4 failed 2 of 2, and b4 is the
scenario where the agent stops for approval. Three distinct rationalizations,
verbatim:

> "no commit (you didn't ask; code and ledger are in sync in the working tree)"

> "committing a 'blocked' verdict before you've seen the pushback seemed presumptuous"

> "Left uncommitted since you didn't ask me to commit"

Both treat committing as needing authorisation — normally correct, which is why a
bare "never leave it dirty" loses to it. Hence invariant 8 now names the default
it overrides and separates committing from merging and pushing.

## A collision the first edit introduced

The stop-gate said "propose the change and end your turn" without saying *where*
the proposal goes. B4 wrote it into seven ledger files and stopped — colliding
head-on with invariant 8, and it said so:

> "Note that contract invariant 8 asks the ledger not to be left dirty at session
> end, so this wants a commit once you've read D-004."

Per `writing-skills`, exemption clauses do not scope, so the fix is not
"invariant 8 does not apply while proposing". The rules were restructured so they
cannot collide: an unapproved plan change is **text in the reply**, never edits on
disk; factual corrections are explicitly not gated and commit normally.

## A scenario expectation that was wrong

A4's `manual` note asked whether the agent stopped for agreement before building
CSV export. It should not stop. R-004 was a requirement the user approved at
kickoff that merely lacked a feature row, and the `roadmap` skill's own classify
table already says a feature row for an existing requirement needs no decision.
Grading A4 as needing a stop would have made the harness demand worse behaviour.
The stop-gate is now scoped to the observable difference — new, reworded, or
out-of-scope requirement stops; missing feature row proceeds — which is B4's case
and not A4's.

## Harness changes

- `run.js canary` — the only check that can see the registry cache.
- tier0 `the installed skill bodies match the repository byte for byte` — catches
  the disk cache. Necessary, and not sufficient; it was green throughout.
- `inspect().extraWorktrees` — B3 satisfied the one-in-progress invariant by
  creating a real git worktree, which is legitimate and left its work invisible to
  every predicate. Its PASS was largely vacuous. Now reported, so a green that
  means "nothing changed here" is at least a loud one.
